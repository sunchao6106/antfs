# s3-scope-rulings — 四项否决的论证与边界

## 1. versioning 家族

- 冲突对象:s3-gc 已锁死点模型(用户拍板 2026-10-14:删除/覆盖 = blob 同请求墓碑 +
  行 state=0,GC 只清行)。开版本化 = versioned 桶删除/覆盖须**保留**旧行、GC 增加版本
  过期/数量上限维度——已锁语义在特定桶上被推翻,模型分裂(两类桶两套 GC/遮蔽规则)。
- 若未来真要重开:须新裁决推翻本裁定 + s3-gc MODIFIED 回写 + GC/遮蔽/配额(`used_bytes`
  记账口径也要分叉:非当前版本计不计配额)——牵动面远超"一个功能"。
- Object Lock(合规保留)依赖 versioning,同案否决。

## 2. 虚拟主机风格路由

- 无技术冲突,纯部署形态决策:路径风格 `/{bucket}/{key}` 已是 D5 锁定形态;虚拟主机要
  域名/通配证书/DNS 运维面,而 antfs 的部署形态(内网/集群内直连)用不上。
- 边界:`Host` 头解析逻辑不引入,不给"预留钩子"。

## 3. 多租户计费

- 边界划清:**桶级存储配额(硬限)已落地**且保留——配额是**管控闸**(写不进去),
  计费是**对账系统**(用了多少、多少钱)——后者需要用量采集、费率、账单流,属运营系统
  范畴,塞进存储网关是职责错位。
- `used_bytes` 记账(为配额服务)天然可导出用量,但 antfs 本身不提供计费能力。
- 追认(2026-10-15,用户拍板「计费不做」):**计量导出 / 用量指标暴露(L0 类)亦不做**——
  `used_bytes` 只为配额守卫服务,不对外成时间序列;后续勿再提案。

## 4. 删除复活(Undelete)

- 死点模型直接推论:删除 = blob 墓碑(引擎墓碑不可逆)+ 行 state=0(仅 GC 记账窗口,
  对 S3 API 不可读)。引擎侧 `delete_is_irreversible_and_key_stays_occupied` 不变量早已
  如此;S3 层宣告与引擎一致的不可逆性。
- 垃圾箱/回收站类语义同案。

## 追认(第二批,2026-10-15 当日)

- **虚拟主机风格路由:翻案**——原「永久拒绝」解除,转**后续队列**(用户裁定排队尾
  实现:Host 重写中间件 + `s3.virtual_host_domain` 配置、默认关,路径风格并存;见
  s3.md 矩阵行)。本档首批其余四项不动。
- **外部凭证源(LDAP / Active Directory / OIDC / 云 IAM 联邦身份):永久拒绝**——
  凭证体系只走内建 MetaStore `s3_credentials`(operator token 管理道签发/吊销);
  外接身份源属网关之外的组织 auth/SSO 层职责,永不进网关功能面。

## 重开程序

任一项重开 = 显式新裁决 + 本档 + 对应设计文档 MODIFIED 回写;不得以"顺手实现"路径复活。
