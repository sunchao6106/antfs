# p1-scheduler-lock — 决策论证

## 三方案对比

| 方案 | 形态 | 得 | 失 |
|---|---|---|---|
| **A(拍板)** | master 只决策 + store 后台 worker 执行 | 零新角色/零新运维面;故障域=各节点;实现量最小(复用数据面+心跳上报);D1 与 Ambry 总原则契合最好 | 带宽仲裁只到 master 任务配额粒度,无集群级集中限速器 |
| B | A + 预留拆分接缝(任务接口按可外部接管抽象) | 独立化路径顺 | 投机抽象(违 CLAUDE.md 简单优先);真拆时协议照样重设计 |
| C | 独立 scheduler 节点(CubeFS 蓝本一步到位) | 集群级带宽集中仲裁;后台重活与数据面资源隔离;超大规模成熟路径 | 新角色=部署/监控/升级+自身高可用选主;实现量最大;Ambry 偏差最大;当前无实测需求 |

## 拍板依据(A)

1. D5 EC 的执行天然局部化:编码单元 = 封存段,数据在段 owner 节点本地;跨节点的只有校验分片
   散写(HTTP 数据面现成)。
2. 再复制/均衡的执行现状已是拉式(master 只下发目标,BOOTSTRAP 自拉)——A 无缝衔接。
3. 唯一由 C 独占的价值(集群级带宽仲裁)在当前阶段无实测需求;P2 真机基线里后台×前台争抢数据
   出现前不配立项。
4. A 是 C 的真子集(演进不浪费):重开独立化时 A 的worker 语义可平移,协议按届时需求重设计。

## 规模触发条件(重开门槛)

节点数带来的后台任务带宽争抢 **实测出现**(指标口径:store 吞吐/尾延迟在前台压测中被后台任务
显著拖累的观察记录),且 master 任务配额机制被证明不够用 → 重开 P1,单独 change。
